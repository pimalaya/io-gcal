# On io-http 0.7: the request head checked, the URL built by the family helper

A dependency bump before the release, with the two items the family audit of 2026-11-13 left for it (the remainder of GCAL-09, low, and FAM-11). Too small for a change folder: it went straight to landing.

## The bump

io-http goes from 0.6 to 0.7 and the dev-dependency io-oauth from 0.5 to 0.6, itself on io-http 0.7, so one io-http remains in the graph (`cargo tree -i io-http`). Nothing stopped compiling, in src/, tests/ (the live suite tests/google.rs and its JWT bearer client included) or examples/: this crate never printed an `HttpAuthBearer`, and the suite touches none of what io-oauth 0.6 changed. The lockfile also moved rsa from 0.10.0-rc.20 to 0.10.0 and crypto-bigint to 0.7.11, and dropped rand and chacha20, all behind io-oauth. The bump is breaking for a caller all the same, since `GcalSendError::Send` carries io-http's `Http11SendError` and every constructor takes its `HttpAuthBearer`.

## The request head

whole-stash-and-encoded-ids left the bearer token, the content type and the method written as given, waiting for the check io-http was to make. It makes it now: `Http11Send` refuses, at its first resume and before any write, a method or a header name that is not a token and a header value holding CR, LF or NUL. `GcalSend::resume` turns that refusal (`Http11SendError::InvalidRequest`) into `GcalSendError::InvalidRequest`, the variant an id or an entity tag is already refused with, so a caller matches one variant for every request stopped before the wire; left alone it came back as `GcalSendError::Send`. The reason is io-http's message, which names the header and not its value: a refused token is not printed. The constructors stay infallible (`get`, `delete`, `post_empty`, `with_method`), which is what the wait was for.

The entity tag check of `with_guard` stays: it is stricter (every control character) and refuses at construction.

## The URL

`gcal_api_url` is now a wrapper over `io_http::rfc3986::path::http_url_build(GCAL_API_BASE, segments)`. The two were compared before the swap: same base handling (`pop_if_empty`), same encoding (`path_segments_mut`), same refused segments (empty, `.`, `..`, a tab or a line break), the first bad segment reported in both. The errors are mapped so that nothing a caller sees moves: `InvalidSegment` to `InvalidRequest` with the former reason, `InvalidBaseUrl` to `ParseUrl`. tests/paths.rs (the 29 id-taking requests under two hostile ids, and the six refused ids in each position) and the per-resource suites pass unchanged.

## Tests

`refuses_a_token_a_method_or_a_content_type_holding_a_line_break`, in tests/send.rs. Against the former code on io-http 0.6 it failed with `expected InvalidRequest, got Yielded(WantsWrite(..))`, the bytes holding `Authorization: Bearer fake-token`, CR LF, `X-Injected: 1`; on io-http 0.7 before the mapping, with `got Complete(Err(Send(InvalidRequest(InvalidHeaderValue("Authorization")))))`. No existing test changed. The live suite was compiled, not run.

Capabilities moved: requests (added: No value of the caller adds a line to the request).
